# FluteBand AI — архитектура MVP

## 1. Общая схема

```
┌─────────────────────────── PWA (телефон, браузер) ───────────────────────────┐
│  Камера/файл → превью и кадрирование → POST /recognize (multipart)           │
│                                                                              │
│  ядро (чистые ES-модули, без DOM):                                           │
│    xml.js → musicxml.js → score.js   (MusicXML → внутренняя модель)           │
│    chords.js / harmony.js            (аккорды ↔ ноты, достройка гармонии)     │
│    transpose.js                      (тональность, профили инструментов)     │
│    accompaniment.js                  (бас + аккорды по ритму: вальс, марш…)   │
│    midi.js                           (экспорт .mid)                          │
│                                                                              │
│  браузерный слой: synth.js (Web Audio + SoundFont), transport.js (темп/луп),  │
│    camera.js (getUserMedia), storage.js (IndexedDB), app.js (UI)             │
└───────────────────────────────────┬──────────────────────────────────────────┘
                                    │ HTTPS (только для распознавания)
                    ┌───────────────▼────────────────┐
                    │ OMR-сервис (Python/FastAPI)     │
                    │  /health  /engines  /recognize  │
                    │  движки: oemer | homr | audiveris (CLI) │
                    │  выход: MusicXML                │
                    └────────────────────────────────┘
```

**Принцип:** распознаётся только **грамматика** страницы (ноты, аккорды, тональность, размер). Аккомпанемент **генерируется на устройстве** из этой грамматики. Поэтому:
- нет передачи и хранения аудио,
- темп/транспонирование меняются без артефактов высоты тона,
- уже распознанная пьеса работает офлайн навсегда.

## 2. Внутренняя модель (ScoreDoc)

```jsonc
{
  "id": "uuid",
  "title": "Ode to Joy",
  "composer": "L. van Beethoven",
  "tempo": 96,                                  // BPM, четверть = 1 доля
  "meter": { "beats": 4, "beatType": 4 },
  "key": { "tonic": "D", "mode": "major", "fifths": 2 },   // концеpтный (звучащий) строй
  "source": { "kind": "omr" | "manual" | "demo", "engine": "oemer 0.1.x", "confidence": 0.82 },
  "tags": ["класс 2", "домашка"],               // теги библиотеки (индекс IndexedDB, поиск и фильтр)
  "cover": "data:image/jpeg;base64,…",           // миниатюра снятой страницы (~2 КБ) для списка библиотеки
  "pages": 2,                                    // сколько страниц сборника собрано в одну пьесу
  "pageStarts": [0, 8],                          // с какого такта начинается каждая страница
  "pageCovers": ["data:…", "data:…"],            // миниатюры остальных страниц
  "measures": [
    {
      "index": 0,
      "events": [ { "beat": 0, "dur": 1, "pitches": [62], "voice": "melody" } ],
      "harmony": [ { "beat": 0, "dur": 4, "symbol": "D" } ]
    }
  ]
}
```

Правила модели:
- `beat` и `dur` — в **четвертных долях** (единый знаменатель для 4/4, 3/4, 6/8 и т.д.).
- `pitches` — MIDI-номера (60 = C4).
- `voice` — `melody` (мелодия, блокфлейта), `bass` (нижняя строка) или `inner` (средние голоса, например
  правая рука фортепиано). На странице сборника «фортепиано + блокфлейта» мелодия берётся с **верхней строки**
  первой партии, остальные строки и партии становятся аккомпанементом; для одноголосных нот всё остаётся
  мелодией (`musicxml.js`, решения №32–33).
- `harmony` — аккордовые символы; при отсутствии в источнике достраиваются `harmony.js`.
- Всё, что не удалось распознать, помечается флагом `lowConfidence` — UI подсвечивает такие такты для ручной правки.
- `tags`, `cover`, `pages`, `pageStarts`, `pageCovers`, `pageSources` — поля библиотеки: их добавляют
  `library-index.js` и `score-pages.js`,
  в саму музыкальную модель они не вмешиваются, поэтому экспорт MusicXML/ MIDI от них не зависит.
- `pageStarts` — это и есть порядок страниц: сборка, вставка и перестановка пересобирают такты по страницам
  (`rebuildScore`) и перенумеровывают их подряд, поэтому «дыр» в нумерации после вставки в середину не бывает.

## 3. Что где считается

| Задача | Модуль | Тестируется в Node |
|---|---|---|
| Имена нот ↔ MIDI ↔ частоты | `pitch.js` | да |
| Разбор аккордовых символов | `chords.js` | да |
| Определение аккорда по набору нот | `harmony.js` | да |
| Транспонирование и профили инструментов | `transpose.js` | да |
| Разбор XML / MusicXML → ScoreDoc | `xml.js`, `musicxml.js` | да (двухголосие, `<backup>`, мелодия с верхней строки при фортепиано + блокфлейте) |
| Подготовка снимка к распознаванию | `image-prep.js`, `image-stats.js` | да (тесты на синтетических пикселях) |
| Выравнивание страницы и света | `perspective.js` | да (гомография, углы, карта бумаги, имитация фото) |
| Замер на настоящих сканах (подготовка, время, повторяемость, сверка фактов) | `tools/real-bench.mjs` + `tools/vision-client.mjs` | нет (стенд, не модуль приложения) |
| Правка типовых ошибок распознавания | `score-fixes.js` | да |
| Хранение и поиск в библиотеке (теги, готовые подсказки, порядок, сводка) | `library-index.js` | да |
| Сборка одной пьесы из нескольких снятых страниц (вставка, перестановка, удаление) | `score-pages.js` | да |
| Генерация аккомпанемента | `accompaniment.js` | да |
| Экспорт MIDI (SMF type 1) | `midi.js` | да |
| Синтез звука | `synth.js` | нет (Web Audio) |
| Транспорт: темп, луп, метроном | `transport.js` | нет (Web Audio) |
| Камера, хранение, UI | `camera.js`, `storage.js`, `app.js` | нет |
| Клиент сервиса распознавания и адрес сервиса | `recognition.js` | да (разбор ответов, адрес: свой origin или внешний) |

Все «да» — чистые ES-модули без DOM: это позволяет прогонять `node --test` и не ловить регрессии в музыкальной логике.

## 4. Аккомпанемент: правила генерации

Вход: такты с гармонией (аккорд + длительность) и мелодией. Выход: список событий `{startBeat, durBeats, midi[], velocity, role}`.

Стили (выбираются автоматически по размеру и темпу, можно задать вручную):

| Стиль | Размер | Рисунок |
|---|---|---|
| `waltz` | 3/4 | бас на 1-й доле, аккорд (3 звука) на 2-й и 3-й |
| `march` (oom-pah) | 4/4, темп ≥ 80 | бас, аккорд, бас(квинта), аккорд |
| `ballad` | 4/4, темп < 80 | бас половинами, аккорд выдержанный, тише |
| `arpeggio` | 4/4/6/8, andante | разложенный аккорд восьмыми: бас-5-8-3-5-8-3-5 |
| `blockChords` | любой | аккорд на каждую долю (минимальный, если гармония бедная) |

Дополнительные правила:
- Бас играется в октаве `C2–C3`, аккорды — `C3–C4` (ниже мелодии, чтобы не мешать).
- «Тяжёлые» доли получают больший velocity; аккорд не дублирует мелодию (если мелодия звучит в аккордовой зоне — убираем дублирующиеся ступени).
- Если аккорд не определён — берём предыдущий; если его нет — строим по тональности (I).
- Каденция: при смене гармонии бас всегда берёт основной тон, при `slash`-аккорде (C/G) — указанный бас.

## 4а. Звук: два движка, один тракт

| Движок | Источник | Вес | Когда используется |
|---|---|---|---|
| встроенный синтез | треугольник + обертоны + фильтр, Web Audio | 0 | всегда; работает без интернета |
| `royal` | Salamander Grand Piano (запись рояля, CC BY 3.0) | 17 сэмплов, 3.5 МБ | по выбору пользователя: лучший тембр |
| `compact` | FluidR3_GM, MIT (mp3-сэмплы) | 49 сэмплов, 1.2 МБ | по выбору: слабый интернет или мало места |

Правила:
- Опорные ноты: у записи рояля каждая третья нота диапазона C2–C6, у компактного банка — все ноты; играем
  ближайшим сэмплом, сдвиг не больше полутора полутонов.
- Сила нажатия: в свободных банках одна запись на ноту, поэтому тихая игра имитируется громкостью и
  фильтром (тише и глуше) — так минус не «звенит» на piano.
- Сэмплы скачиваются один раз и лежат в IndexedDB рядом с библиотекой пьес; повторный выбор банка не
  обращается к сети (проверено самоконтролем: 0 запросов).
- Плеер и офлайн-рендер WAV создаются одним классом `PianoSynth` и получают одни и те же сэмплы,
  поэтому экспортированный файл звучит как приложение.
- Лицензии обоих банков свободные и требуют только указания авторства — оно хранится в `sampler.js` и
  показывается в интерфейсе рядом с названием банка.

## 5. Сервер распознавания

`server/` — FastAPI, плагинные движки:

| Движок | Лицензия | Требует | Роль |
|---|---|---|---|
| `homr` | свободная | Python + ONNX (модели с HF) | **основной, проверен**: F1 83.6% на стенде, ~7 с на страницу |
| `oemer` | MIT | Python + onnxruntime (CPU) | установлен, но с onnxruntime 1.30 падает (отрицательные `pads` в ConvTranspose) |
| `audiveris` | AGPL | Java (JRE входит в установщик) | резерв/сверка; Java в системе пока нет |
| `stub` | — | — | отдаёт эталонный MusicXML для проверки клиента без OMR |

Перед отправкой на сервер снимок проходит подготовку на устройстве — три шага, каждый со своей проверкой:

1. **Оттенки серого** (`image-prep.js`, `image-stats.js`) — движок всё равно работает с яркостью.
2. **Выравнивание наклона** (`perspective.js`) — телефон почти никогда не смотрит на сборник сверху, поэтому
   лист на снимке трапеция. Находим четыре угла листа (крайние точки маски бумаги по направлениям `x±y`),
   считаем гомографию в прямоугольник и пересэмплируем с билинейной интерполяцией: строки становятся
   горизонтальными. Ровный снимок не трогаем — лишнее пересэмплирование только вредит.
3. **Выравнивание света** (`perspective.js`) — на фото с телефона один край листа бывает темнее стола у другого.
   Считаем **карту уровня бумаги**: кадр делится на блоки, в каждом берётся перцентиль только тех пикселей, что
   прошли «затравку» по порогу Оцу, пустые блоки (стол) берут уровень у соседей, и карта растягивается
   билинейно. Дальше либо делим пиксели на местный уровень (свет выравнивается), либо используем карту как
   местный порог бумаги. Это принципиально: с общим порогом по кадру маска бумаги отрезала затенённую часть
   листа — на замере это давало 69.8% вместо 86.7% (см. `docs/omr-photo.md`).
4. **Кромка по краям** (`image-prep.js`, `edgeTrimBounds`) — после выпрямления у самых краёв может остаться
   полоса тени и границы листа. Ищем её как непрерывную тёмную полосу от края, останавливаясь на первой светлой
   строке, с пределом 3.5% стороны: заголовок или нотную строку у края это не задевает. На 12 фото имитации
   кромка после выравнивания света уже не появляется (замер: 0.97 и 0.92 от яркости середины против 0.42
   на исходном фото), поэтому шаг — страховка для случая, когда лист занимает весь кадр. Обрезка контраста
   на вырожденном кадре (одна бумага) не растягивается, иначе бумага почернела бы.

Отдельная опция `flattenAfterContrast` (по умолчанию **выключена**) выравнивает свет ещё раз после контраста:
кромка становится почти идеальной (0.996), но на пресете «наклон 5°» это стоило 2.4 п.п. точности
(86.7% → 84.3%), поэтому в приложении шаг не включён — замер в `docs/omr-photo.md`.

После этого — поиск листа, растяжение контраста внутри листа, обрезка полей вокруг нот. Если лист занимает
весь кадр, границы не трогаются; увеличение и бинаризация по умолчанию выключены — на замерах они снижали
точность. Замеры влияния: `docs/omr-prep.md` (ровные страницы) и `docs/omr-photo.md` (имитация фото).

Контракт: `POST /recognize` (multipart: `image`, необязательные `engine` и `mode`) →
`{ "musicxml": "...", "engine": "...", "mode": "full|melody", "melody": {…}, "elapsedMs": 0, "warnings": [] }`.
Ограничения бесплатного тарифа учитываем: max размер картинки (длинная сторона ≤ 2000 px), таймаут, очередь, кэш по хэшу изображения.

**Два режима распознавания.** `full` — вся страница, как раньше. `melody` — движку отдаётся только
мелодический стан: `server/melody.py` находит станы геометрически (порог Оцу, ряды с чернилами ≥ 0.25
ширины, группы по пять линеек с равным шагом, системы по разрыву ≤ 12 шагов), отрезает верхний стан каждой
системы с запасом сверху 3.2 шага и снизу 2.2 шага, склеивает полосы с перекрытием 25% и отдаёт движку
узкую картинку. Фортепианная партия в минус не идёт (решение 20), поэтому её распознавание — чистая
потеря времени: дома 9.6 с против 32.4 с на той же странице, мелодия совпала нота в ноту (86 из 86).
Если стан не нашёлся, сервис **не выдумывает** результат: распознаётся вся страница, а в ответе идут
`mode: "full"` и предупреждение. Пустые такты (флейта молчит, играет фортепиано) помечаются паузой
(`measure.rest`), иначе минус сдвинулся бы по времени.

**Очередь.** Распознавания выполняются по одному (`_RECOGNIZE_LOCK` в `server/engines.py`): движок
процессорный, на бесплатном тарифе два ядра, и два одновременных распознавания только отбирали бы их друг
у друга. Замер на контейнере с двумя ядрами: два одновременных запроса заняли 23 с и 46 с при собственной
работе ~23 с у каждого — то есть второй честно ждал первый, а не портил ему результат.

### Где живёт сервис: свой адрес или внешний

Приложение — статика, сервис — отдельный процесс, и они могут стоять на разных бесплатных хостингах:

| Режим | Адрес в настройках | Куда идёт запрос | Когда так делают |
|---|---|---|---|
| рядом | пусто (по умолчанию) | `api/recognize` — **от каталога приложения** | локальный запуск (`tools/serve.mjs` проксирует `/api/*` на сервис), всё на одном хосте |
| внешний | `https://ваш-сервис.example.com` | `https://ваш-сервис.example.com/recognize` | приложение статикой на Netlify / Cloudflare Pages / GitHub Pages, сервис на Hugging Face Spaces / Render |

- Адрес по умолчанию считается от каталога приложения (`new URL('api/recognize', location.href)`), а не от
  корня сайта: на GitHub Pages приложение лежит в подкаталоге (`имя.github.io/fluteband/`), и путь от корня
  увёл бы запрос в чужой сайт. В корне сайта получается ровно тот же `/api/recognize`, что и раньше.
- Адрес хранится в настройках устройства (`storage.js`, поле `omrUrl`) и вводится на экране «Сканировать»;
  кнопка «Проверить связь» дёргает `/health` и показывает список доступных движков.
- Схему можно опустить (`omr.example.com` → `https://omr.example.com`) — так проще писать адрес руками.
- У сервиса открыт CORS (`allow_origins=["*"]`), поэтому кросс-доменный запрос проходит; это проверено
  самоконтролем: приложение на `127.0.0.1:3030` распознаёт страницу через `127.0.0.1:8000` (движок homr, 4 такта),
  и в журнале ресурсов браузера видно, что запрос ушёл именно на внешний адрес.
- Камера работает только в защищённом контексте: на телефоне это HTTPS-адрес хостинга или localhost.

### Публикация: три пакета, три площадки

| Что | Чем собирается | Что получается | Куда выкладывается |
|---|---|---|---|
| Приложение | `npm run build:static` | `dist/` — 46 файлов, 0.45 МБ, относительные пути, `.nojekyll`, `_headers`, имя кэша оболочки = хеш содержимого | Netlify (корень, `netlify.toml` уже в репозитории), Cloudflare Pages (корень) или GitHub Pages (подкаталог) |
| Сервис, бесплатно | `npm run pack:space:gradio` | `dist-space-gradio/` — 21 файл, 150 МБ (из них 150 МБ — модели движка), `app.py`, `requirements.txt`, `packages.txt`, `.gitattributes` с git-lfs, `README.md` с шапкой (`sdk: gradio`, `app_port: 7860`) | Hugging Face Spaces, **SDK: Gradio** (единственный бесплатный вариант у Hugging Face) |
| Сервис, Docker | `npm run pack:space` | `dist-space/` — сервер, `Dockerfile`, шапка (`sdk: docker`) | Hugging Face с платным планом, Render, Fly.io |

- **Почему Gradio.** Docker-пространства на Hugging Face требуют платного плана (PRO), бесплатными остались
  Gradio (до двух на аккаунт, железо ZeroGPU). Сервис процессорный, поэтому `app.py` собирает наше FastAPI и
  **монтирует в него страницу Gradio** (`gr.mount_gradio_app(api, demo, path="/")`): наши маршруты объявлены
  раньше и остаются на месте, а требование «SDK: Gradio» выполняется. Приложению менять нечего.
- **Модели лежат в репозитории пространства** (git-lfs), а не скачиваются при первом запросе: диск
  пространства непостоянный, и скачивание во время запроса ломало распознавание, когда рядом шёл второй
  запрос (оба процесса делили один архив — `FileNotFoundError`). В облаке не скачивается ничего, и это
  проверено запуском сервиса с выключенной сетью. В Docker-варианте набор можно задать ключом
  `FLUTEBAND_HOMR_GPU=no|auto|force` (там homr 0.7.0): без него движок сам выбирает fp16 там, где видит
  видеокарту. В Gradio-пространстве ключ бесполезен — у homr 0.6.2 такого флага нет (см. ниже).
- **Прогрев при старте** только читает модели с диска (150 МБ). Полное пробное распознавание при старте
  занимало очередь и задерживало первый запрос ученика: измерено 53 с против 28 с, при том что следующий
  запрос быстрее не становился.
- **Набор моделей привязан к версии движка, а версия — к версии Python.** В базовом образе
  Gradio-пространства Python 3.10, и pip ставит `homr 0.6.2` (на 3.11 — 0.7.0: `rapidocr` требует 3.11);
  версии ищут разные файлы (`..._331` против `..._396`), а флага `--gpu` у 0.6.2 нет. Поэтому версия
  движка закреплена в `requirements.txt` шаблона, в `models/` лежит набор ровно этой версии, сборщик
  пакета отказывается собирать несовпадение, при старте пространство сверяет набор с ожиданиями движка
  (`check_models`) и пишет расхождение в журнал, а `server/engines.py` спрашивает у движка, знает ли он
  `--gpu`, и передаёт флаг только тогда. Проверено запуском с выключенной сетью: скачиваний нет.
- **`packages.txt` содержит только имена пакетов** (пять строк, без пояснений): Hugging Face ставит их
  командой `xargs -r -a packages.txt apt-get install -y`, где каждое слово становится именем пакета, и
  пояснение на русском превращается в пакеты `#`, `системные`, `библиотеки` — сборка падает с
  `Unable to locate package #` (проверено настоящей сборкой пространства). Сборщик пакета и юнит-тесты
  это проверяют, а `Dockerfile.test` ставит библиотеки из того же файла той же командой, поэтому ошибка
  больше не пройдёт мимо локальной проверки.
- Сборка приложения **отказывается собираться**, если в файлах есть пути от корня сайта, если в офлайн-оболочке
  указаны отсутствующие файлы или если модуль не попал в список кэша. Имя кэша — хеш содержимого, поэтому
  после выпуска ученик получает новую версию, а не старую из кэша.
- Проверка `npm run check:static` поднимает `dist/` в подкаталоге (как на GitHub Pages) и прогоняет
  офлайн-проверку **на этот адрес**: service worker встаёт с областью подкаталога, оболочка ложится в кэш,
  страница открывается с выключенной сетью. `npm run check:netlify` делает то же для корня сайта,
  `npm run check:netlify:pretty` — для случая, когда хостинг отдаёт главную страницу перенаправлением.
- Для Netlify в репозитории лежит `netlify.toml`: команда сборки, папка публикации, выключенные «красивые
  адреса» (`pretty_urls = false` — иначе `/index.html` превращается в `/`, а это адрес запуска PWA) и
  заголовки (service worker без кэша, манифест как `application/manifest+json`). Те же заголовки попадают
  в `dist/_headers`, поэтому работают и при выкладке готовой папки. Прокси распознавания через Netlify не
  используется: у прокси-запросов предел 26 секунд, а плотная страница распознаётся 130 секунд.
- Образ сервиса ставит движок `homr`, скачивает его модели на сборке (`homr --init`, чтобы первый запрос
  ученика не ждал загрузки), добавляет системные библиотеки для OpenCV и запускает контейнер не от root.
  Gradio-пакет теми же библиотеками управляет через `packages.txt` — так их ставит сам Hugging Face.
- Сборщик Gradio-пакета проверяет себя сам и **отказывается собирать** негодное: не тот SDK в шапке, нет
  правила git-lfs, попал набор fp16 вместо процессорного, нет моделей, в пакет затесался `Dockerfile` или
  локальные пакеты `server/deps`.
- Инструкция по шагам и чек-лист после выкладки — `docs/05-publikaciya.md`.

## 6. Быстрый режим (≤3 с) vs полный (≤15 с)

- **Быстрый**: клиент сам ищет на странице блоки аккордовых символов и строки нот простыми эвристиками (порог по контрасту, шаблоны букв) → сразу предлагает гармонию. Ничего не уходит в сеть.
- **Полный**: изображение → OMR-сервис → MusicXML → модель.
Оба режима сходятся в одну модель, поэтому генератор минуса общий.

## 7. Хранение и приватность

- Пьесы, изображения и MIDI — в IndexedDB устройства.
- Оболочка приложения кэшируется service worker: 40 файлов доступны без сети, поэтому занятие не зависит
  от интернета (проверка: `npm run check:offline` — приложение открывается с выключенной сетью, минус
  строится, встроенный синтез играет без запросов). Распознавание — единственный шаг, которому нужна сеть.
- Вместе с пьесой хранится маленькая обложка снятой страницы (~2 КБ на страницу), чтобы список библиотеки
  был узнаваемым; полноразмерные снимки не сохраняются, если пользователь сам их не сохранил.
- На сервер уходит только изображение страницы, без аккаунта и без привязки к пользователю; сервер не хранит изображения (обработка в памяти, лог без картинок).
- Никакой публичной раздачи распознанных сборников — только личная библиотека ученика.

## 9. Бесплатные инструменты (итоговый список)

Языки и рантаймы: JavaScript (ES2022) + Node.js 24 (есть), Python 3.13 (есть), Java для Audiveris (позже, бесплатно).
Фреймворки: FastAPI + Uvicorn (MIT/BSD), чистый Web Audio API (без платных SDK).
OMR: oemer (MIT), homr, Audiveris (AGPL) — резерв.
Звук: Salamander Grand Piano (CC BY 3.0), FluidR3_GM (MIT) — только для фортепианного минуса.
Ноты и данные: MuseScore / LilyPond (для синтетических тестов), IMSLP (public domain).
Звук: FluidSynth (LGPL, для офлайн-генерации) и свободные банки Salamander Grand Piano (CC), GeneralUser GS.
Хостинг: Cloudflare Pages / GitHub Pages (статика) + бесплатный серверный тариф для OMR; локальная разработка — `python -m http.server` / статический сервер Node.
Тесты: `node:test` (встроен), pytest (для сервера).
Проверка «глазами»: мультимодальные модели бесплатного доступа (в текущей среде — `qwen3.8-flash`) через
`tools/vision-probe.mjs`: инструмент отправляет картинку и вопрос, поэтому подготовку снимка можно проверить
не только метрикой, но и описанием того, что реально видно (`tools/photo-compare.mjs` делает картинки для сравнения).
Всё перечисленное — без оплаты и без проприетарных лицензий.
