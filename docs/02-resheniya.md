## Следствия выбора PWA (пункт 13) — что меняется относительно Flutter

**Плюсы, которые мы получаем:**
- Ноль установок для пользователя: открыл ссылку → «Добавить на главный экран» → иконка как у приложения.
- Бесплатный хостинг статики (GitHub Pages / Cloudflare Pages), обновления мгновенно, без модерации магазинов.
- Камера доступна через `getUserMedia` (на iOS — Safari 14.3+; для PWA нужен HTTPS).
- Звук: Web Audio API. Мы синтезируем аккомпанемент из внутренней модели нот, поэтому **замедление и транспонирование не портят высоту тона** — это принципиальное преимущество перед воспроизведением готового аудиофайла.
- Один код под Android/iOS/десктоп, разработка и тестирование целиком в этой папке.

**Минусы и как закрываем:**
| Ограничение PWA | Решение |
|---|---|
| Нет тяжёлого OMR на устройстве | Распознавание — на сервере (бесплатный тариф) |
| Сервер бесплатного тарифа «засыпает» | Клиент показывает статус, прогревает сервер, есть офлайн-библиотека уже распознанных пьес |
| iOS: жёсткие лимиты кэша/офлайна | Кэшируем оболочку + распознанные пьесы в IndexedDB, MIDI/аудио генерируем на месте |
| MP3-экспорт без ffmpeg | Двухшагово: WAV (нативно) + опционально MP3 через свободный JS-энкодер (lamejs) или сохранение WAV/MIDI как основного формата |
| Аудио в фоне на iOS ограничено | Учебный сценарий — экран активен; предупреждаем в UI |

Отказ от Flutter не меняет архитектуру ядра: **вся музыкальная логика — отдельные ES-модули**, которые при желании переносятся в Flutter/Dart или переиспользуются через WebView.

## Следствия выбора public-domain тестовых данных (пункт 15)

- Для проверки точности OMR берём сканы/PDF из общественного достояния (IMSLP, MuseScore public domain, IMSLP-подобные архивы) и синтетические страницы, сгенерированные MuseScore/LilyPond (бесплатные).
- Ограничение: на них не проверить «именно ваш сборник». Поэтому в приложении **обязателен ручной режим правки/ввода аккордов** — если распознавание ошиблось, ученик всё равно получит рабочий минус.
- Ваши собственные фото можно будет протестировать позже, локально, без публикации.

| 26 | Разделение приложения и сервиса | **Приложение — статика, сервис — по настраиваемому адресу** | Адрес сервиса хранится в настройках (`omrUrl`): пусто — свой `/api`, иначе внешний адрес; у сервиса открыт CORS, чтобы их можно было разложить по разным бесплатным хостингам |

| 30 | Замер на настоящих нотах (десятый круг) | **Мерить на настоящем материале и не заявлять точность без эталона** | Стенд `tools/real-bench.mjs` (`npm run bench:real`) гоняет приложение по библиотечным сканам и по файлам пользователя. Измеряется то, что проверяемо: подготовка, время, повторяемость, согласие «ровный скан ↔ фото», сверка фактов с независимым чтением модели. «Точность в процентах» на настоящих сканах **не заявляется** — эталонной расшифровки нет, и в `docs/omr-real.md` это написано прямо |
| 31 | Скорость распознавания (десятый круг) | **Честно показать, что цель ≤15 с не выполняется на плотной странице** | Замер: 14.8–46.0 с на страницу, «Финская» (фортепиано + блокфлейта) — 34.7 и 46.0 с. Минус при этом строится за 1–7 мс, подготовка — 41–378 мс. Увеличение мелкой страницы проверено и не помогает; ускорение — отдельная задача (облачный сервис с большим числом ядер, отдача движку одного стана) |
| 32 | Мелодия и фортепиано в сборнике (одиннадцатый круг) | **Мелодия — верхняя строка, читаем все партии** | На странице «фортепиано + блокфлейта» распознавание отдаёт две партии, а в первой — два стана. Приложение читает все партии (у каждой свой счётчик времени внутри такта) и берёт мелодию с верхней строки; самая низкая строка становится «басом», остальные — «средними». Правило «самый высокий голос такта» осталось только для файлов с одной строкой, поэтому одноголосные пьесы разбираются как раньше. Замер: мелодия первой страницы «Финской» 125 нот (57–81) → 86 нот (69–81), в разбор добавилось 78 нот левой руки вместо нот правой |
| 33 | Экспорт MusicXML с фортепианной партией (одиннадцатый круг) | **Голоса не сливать** | Мелодия → голос 1, «средние» (правая рука) → 2, бас → 3. Раньше всё, кроме баса, попадало в голос 1, и при экспорте страницы «фортепиано + блокфлейта» партия правой руки приклеивалась к мелодии. Фортепианная партия при этом не рисуется в пианоле: приложение играет свой минус, а не исходную партию фортепиано |
| 34 | Публикация приложения (двенадцатый круг) | **Статика на бесплатном хостинге, все пути относительные** | Приложение собирается в `dist/` (`npm run build:static`) и выкладывается на Netlify (корень сайта), Cloudflare Pages (корень) или GitHub Pages (подкаталог `имя.github.io/fluteband/`). Сборка отказывается собираться, если в файлах есть пути от корня сайта, если офлайн-оболочка не совпадает с файлами на диске, или если модуль не попал в список кэша. Имя кэша оболочки = хеш содержимого пакета, поэтому после выпуска ученик не остаётся на старой версии из кэша. Проверка `npm run check:static` поднимает пакет в подкаталоге и проверяет офлайн с выключенной сетью, `npm run check:netlify` — то же для корня сайта |

Две ошибки, найденные запуском контейнера, исправлены: проверка установки движка смотрела только в `server/deps` (в контейнере пакет стоит в окружении Python) и в slim-образе не было системных библиотек для OpenCV (`libxcb`, `libgl`) — распознавание падало с `ImportError` |
| 36 | Площадка для приложения: Netlify (тринадцатый круг) | **Netlify основной, `netlify.toml` в репозитории, «красивые адреса» выключены** | Самый короткий путь: перетащить содержимое `dist/` на `app.netlify.com/drop` (без репозитория и без сборки) либо подключить репозиторий — тогда `netlify.toml` сам задаёт команду `npm run build:static`, папку публикации `dist` и заголовки (service worker без кэша, манифест как `application/manifest+json`). «Красивые адреса» Netlify превращают `/index.html` в `/`; приложение кэширует оболочку по конкретным адресам, а стартовый адрес PWA — `./index.html`, поэтому настройка выключена (`pretty_urls = false`) и проверен худший случай: `npm run check:netlify:pretty` показывает, что даже с включёнными «красивыми адресами» офлайн собирается (кэширование оболочки переписано с `cache.addAll` на поштучное, иначе один перенаправлённый адрес отменял установку кэша целиком). Наш сервис процессорный, видеокарта ему не нужна, поэтому собираем Gradio-пространство и **монтируем в него свой FastAPI**: `/health`, `/engines` и `/recognize` остаются теми же, приложению менять нечего. Пакет `dist-space-gradio/` (`npm run pack:space:gradio`) = сервис + `app.py` + модели движка. Поэтому распознавания выстраиваются в очередь (`_RECOGNIZE_LOCK`): ядер на бесплатном тарифе два, и два одновременных распознавания только отбирали бы их друг у друга. **Версия движка закреплена** (`homr==0.6.2`): в базовом образе пространства Python 3.10, pip ставит там старую версию, а версии ищут разные файлы моделей (331 против 396) — с чужим набором движок скачивает свои модели во время запроса (проверено запуском). Набор моделей в пакете соответствует закреплённой версии, при старте пространство сверяет его с ожиданиями движка (`check_models`), а флаг `FLUTEBAND_HOMR_GPU` передаётся только той версии homr, которая его знает. Docker-вариант (`dist-space/`) остаётся для платного плана или другого хостинга |

## Итоговые границы продукта (scope)

**Входит в MVP:**
1. PWA: библиотека пьес, камера, воспроизведение, транспорт.
2. Распознавание печатных нот → мелодия + аккорды + тональность/размер (сервер).
3. Генератор фортепианного аккомпанемента (бас + аккорды по ритму) и его воспроизведение.
4. Темп, метроном, счёт-ин, луп, замедление, транспонирование, профили инструментов.
5. Показ нот (упрощённый) и экспорт MIDI/WAV; библиотека локально.

**Не входит (осознанно):**
- Рукописные ноты.
- Точная копия фортепианной партии из сборника (нота-в-ноту).
- Следование за игроком по микрофону (авто-темп), разбор ошибок, ансамблевые партии.
- Любая публикация/раздача распознанных сборников.
