# Публикация на бесплатном хостинге

Приложение FluteBand AI состоит из двух частей, и выкладываются они на разные бесплатные площадки:

| Часть | Что это | Куда | Деньги |
|---|---|---|---|
| **Приложение** | статические файлы (`dist/`, 46 файлов, 0.45 МБ) | Netlify (проще всего) **или** Cloudflare Pages **или** GitHub Pages | бесплатно, без карты |
| **Сервис распознавания** | Python + ONNX-движок `homr`, Gradio-пространство | Hugging Face Spaces (**SDK: Gradio**) | бесплатно, без карты |

> **Что изменилось у Hugging Face.** Docker-пространства теперь требуют платного плана (PRO), а
> бесплатными остались Gradio-пространства (до двух на аккаунт, железо ZeroGPU). Сервис считает на
> процессоре, поэтому собирается как Gradio-пространство, внутрь которого **монтируется наш FastAPI**:
> адреса `/health`, `/engines` и `/recognize` те же, приложению менять нечего. Раздел 5 — по шагам.

Сервис — это Python и нейросетевой движок, на статическом хостинге он жить не может. Зато он не нужен
для игры: приложение само по себе офлайновое (ПВА, кэш оболочки), а сервис нужен только чтобы превратить
**фото нот** в нотный текст. Готовые `.musicxml` приложение разбирает на устройстве, без сервиса.

## 1. Собрать пакеты

```bash
npm run build:static        # → dist/               (приложение)
npm run check:static        # проверка: подкаталог, service worker, офлайн без сети (GitHub Pages)
npm run check:netlify       # проверка: приложение в корне сайта (Netlify, Cloudflare Pages)
npm run pack:space:gradio   # → dist-space-gradio/  (сервис для бесплатного Gradio-пространства)
npm run pack:space          # → dist-space/         (тот же сервис как Docker-образ — платный план или иной хостинг)
```

`check:static` поднимает `dist/` в подкаталоге (как на GitHub Pages), включает Chrome и проверяет
по-настоящему: файлы оболочки отдаются, service worker встаёт с областью подкаталога, оболочка ложится
в кэш, затем **сеть выключается** и приложение всё равно открывается и строит минус. Если эта проверка
прошла — выкладка не сюрпризов не принесёт. `check:netlify` делает то же самое для корня сайта, а
`npm run check:netlify:pretty` — ещё и с включёнными «красивыми адресами» (см. ниже).

При сборке имя кэша оболочки привязывается к содержимому пакета (`fluteband-shell-<хеш>`), поэтому после
обновления ученик получает новую версию, а не старое из кэша. Руками имя менять не нужно.

## 2. Приложение: Netlify (самый простой путь)

Даёт корень сайта (`https://имя.netlify.app`), HTTPS (нужен для камеры на телефоне), сборку из
репозитория и не требует карты. Ничего доустанавливать не нужно: пакет уже собран и проверен.

### Как выложить готовую папку (без репозитория, 2 минуты)

1. Зайдите на <https://app.netlify.com/drop> и войдите (можно через GitHub, Google или почту —
   бесплатный тариф, карта не нужна).
2. Соберите пакет и перетащите в окно **содержимое** папки `dist/` (не саму папку):

   ```bash
   npm run build:static
   ```

   Внутри должны быть: `index.html`, `js/`, `css/`, `icons/`, `demo/`, `manifest.webmanifest`,
   `service-worker.js`, `_headers`, `.nojekyll`.
3. Готово: адрес будет вида `https://случайное-имя.netlify.app`. В **Site configuration → Change site
   name** можно задать своё имя → `https://fluteband.netlify.app`.
4. Обновление версии — снова `npm run build:static` и снова перетащить папку (или подключить
   репозиторий, тогда обновление идёт по `git push`).

### Как выложить из репозитория (обновления по git push)

1. Загрузите проект в GitHub (или GitLab/Bitbucket) — репозиторий может быть закрытым. Папка проекта
   **пока не является git-репозиторием**, поэтому первый раз нужно её инициализировать:

   ```bash
   git init
   git add -A
   git commit -m "FluteBand AI"
   git branch -M main
   git remote add origin https://github.com/имя/fluteband.git
   git push -u origin main
   ```

   В репозитории нет зависимостей (`package.json` без `dependencies`), а `dist/`, `dist-space/` и рабочие
   каталоги распознавания перечислены в `.gitignore` — на Netlify поедет только исходный код.
2. Netlify: **Add new project → Import an existing project** → выберите репозиторий.
3. Настройки подставятся из `netlify.toml` в корне проекта, проверьте их в форме:
   | Поле | Значение |
   |---|---|
   | Build command | `npm run build:static` |
   | Publish directory | `dist` |
   | Branch to deploy | основная ветка (`main`) |
4. **Deploy**. Сборке не нужны зависимости: `npm run build:static` — это обычный Node-скрипт без
   сторонних пакетов, поэтому она занимает секунды и не тратит минуты сборки. Версия Node закреплена в
   `netlify.toml` (`NODE_VERSION = "20"`), чтобы сборка не зависела от версии по умолчанию на площадке.

### Что уже настроено в `netlify.toml` (менять не нужно)

- **Сборка и папка публикации** — `npm run build:static` и `dist`.
- **«Красивые адреса» выключены** (`pretty_urls = false`). Это важно: иначе Netlify превращает
  `/index.html` в `/`, а приложение кэширует оболочку по конкретным адресам и стартовый адрес PWA —
  именно `./index.html`. Проверено и так и так: даже если эту настройку случайно включить, приложение
  всё равно собирает офлайн-кэш (в `dist/_headers` и в самом service worker есть страховка) —
  см. `npm run check:netlify:pretty`.
- **Заголовки**: service worker отдаётся с `Cache-Control: no-cache` (иначе обновление не доедет до
  ученика), манифест — как `application/manifest+json` (по этому типу Chrome понимает, что приложение
  можно установить). Те же заголовки лежат в `dist/_headers`, поэтому работают и при выкладке папки.
- **Прокси распознавания выключен намеренно.** У прокси-запросов Netlify есть предел **26 секунд**
  ([документация](https://docs.netlify.com/manage/routing/redirects/rewrites-proxies/)), а распознавание
  плотной страницы занимает 130 с на бесплатном тарифе сервиса. Поэтому приложение обращается к сервису
  **напрямую**: адрес вводится на экране «Сканировать» → «Адрес сервиса» (у сервиса открыт CORS).
  Проксировать имеет смысл только быстрые, разреженные страницы; готовый блок для этого лежит
  закомментированным в `netlify.toml`.

> Свой домен подключается бесплатно (**Domain management → Add a domain**), но нужен сам домен —
> бесплатного имени Netlify не выдаёт. Для установки PWA и камеры хватает и адреса `…netlify.app`.

## 3. Приложение: Cloudflare Pages (тоже просто)

Даёт корень сайта (`https://имя.pages.dev`), HTTPS (нужен для камеры на телефоне) и не требует карты.

**Через браузер, без установки программ:**

1. Зайдите на <https://dash.cloudflare.com> и создайте бесплатный аккаунт.
2. **Workers & Pages → Create → Pages → Upload assets**.
3. Имя проекта, например `fluteband` (адрес будет `https://fluteband.pages.dev`).
4. Перетащите **содержимое** папки `dist/` (не саму папку): `index.html`, `js/`, `css/`, `icons/`,
   `demo/`, `manifest.webmanifest`, `service-worker.js`, `_headers`, `.nojekyll`.
5. **Deploy**. Через несколько секунд приложение открывается по адресу вида
   `https://fluteband.pages.dev/index.html`.

**Через командную строку (то же самое, удобно повторять):**

```bash
npx wrangler pages deploy dist --project-name=fluteband
```

Обновление версии — снова `npm run build:static`, затем повторная выкладка (или `git push`, если проект
подключён к репозиторию: Cloudflare Pages собирает ветку сам, команда сборки не нужна).

## 4. Приложение: GitHub Pages (подкаталог)

Приложение проверено и для этого случая: адрес будет `https://имя.github.io/fluteband/`, то есть
приложение живёт **в подкаталоге** чужого корня. Все пути в приложении относительные, `.nojekyll` уже
в пакете.

1. Создайте **публичный** репозиторий (бесплатные Pages — только для публичных репозиториев).
2. Положите содержимое `dist/` в ветку, с которой публикуете:

```bash
git clone https://github.com/имя/fluteband.git && cd fluteband
# скопируйте сюда содержимое dist/
git add -A && git commit -m "FluteBand AI" && git push origin main
```

3. **Settings → Pages → Source: Deploy from a branch**, ветка `main`, папка `/ (root)` → **Save**.
4. Через минуту приложение открывается: `https://имя.github.io/fluteband/index.html`.

Без аккаунта GitHub тоже можно: Pages требует репозиторий, но карту — нет.

## 5. Сервис распознавания: бесплатное Gradio-пространство Hugging Face

**Сначала важное.** Docker-пространства на Hugging Face теперь требуют платного плана (PRO). Бесплатными
остались только Gradio-пространства (до двух на личный аккаунт, железо ZeroGPU). Наш сервис считает на
процессоре, видеокарта ему не нужна, поэтому мы собираем **Gradio-пространство и монтируем в него свой
FastAPI**: адреса `/health`, `/engines` и `/recognize` остаются ровно теми же, что у Docker-варианта, и
приложению менять нечего.

### 5.1. Собрать пакет

```bash
python -c "from homr.main import main; main()" --init --gpu no   # один раз: модели движка для процессора
npm run pack:space:gradio                                        # → dist-space-gradio/
```

Пакет — 21 файл, 150 МБ, из них 150 МБ — три модели движка (ONNX). Версия SDK не фиксируется: Hugging Face
возьмёт свою текущую (проверено локально на gradio 6.28).

**Три ловушки в файлах зависимостей и моделей** (каждая стоила неудачной сборки или лишнего скачивания,
поэтому записаны здесь):

- `packages.txt` читает **`xargs`**, а не apt: `xargs -r -a packages.txt apt-get install -y`. Каждое слово
  в файле становится именем пакета, поэтому пояснения и комментарии там **запрещены**: строка
  `# системные библиотеки` превращается в пакеты `#`, `системные`, `библиотеки`, и сборка падает с
  `Unable to locate package #`. В файле допустимы только имена пакетов, по одному в строке.
- `requirements.txt` читает `pip`, и комментарии он понимает — там пояснения оставлять можно.
- **Набор моделей зависит от версии движка, а версия — от версии Python.** В базовом образе
  Gradio-пространства Python 3.10, и pip ставит там `homr 0.6.2`, которому нужны модели
  `encoder/decoder_pytorch_model_331`; на Python 3.11 ставится 0.7.0 с моделями `..._396`. Флага `--gpu`
  у 0.6.2 нет, поэтому набор моделей нельзя задать ключом — только версией. Версия в `requirements.txt`
  **закреплена** (`homr==0.6.2`), в `models/` лежит ровно её набор. Если менять версию движка — менять и
  набор моделей, иначе движок скачает свои модели во время запроса ученика (замерено: «Downloading 3
  models», первым segnet на 51 МБ). При старте пространство сверяет набор с тем, что движок ищет, и пишет
  расхождение в журнал — там это и будет видно, а не в виде загадочной медлительности.

Чтобы ошибки не повторялись, сборщик проверяет `packages.txt` построчно, требует закреплённую версию
движка и набор моделей именно этой версии, а локальная проверка (`Dockerfile.test`) ставит библиотеки из
того же файла той же командой `xargs`, что и настоящее пространство.

**Почему модели лежат в репозитории пространства.** Диск пространства непостоянный (50 ГБ, стирается при
перезапуске), поэтому без файлов в репозитории движок скачивал бы модели во время запроса. Это не только
медленно: если рядом шёл второй запрос (например, прогрев движка после «сна»), оба процесса качали один и
тот же архив и один из них падал с `FileNotFoundError` посреди распаковки — ошибка найдена запуском
контейнера. Поэтому в облаке **не скачивается ничего**; модели уезжают через git-lfs (правило уже в пакете,
`.gitattributes`). Проверено запуском сервиса **с выключенной сетью** в окружении пространства: демо-страница
распознана за 22 с, ни одного скачивания.

### 5.2. Создать пространство

1. Аккаунт на <https://huggingface.co> (бесплатный).
2. **New Space**: имя `fluteband-omr`, **SDK: Gradio**, шаблон **Blank**, видимость **Public**.
   **Storage Bucket отмечать не нужно**: сервис ничего не хранит (фото обрабатывается во временном
   каталоге и удаляется, кэш результатов — в памяти), а модели лежат в самом репозитории.
3. Загрузите содержимое `dist-space-gradio/` в репозиторий пространства:

```bash
git lfs install                                    # один раз на машине (git-lfs нужен для моделей)
git clone https://huggingface.co/spaces/имя/fluteband-omr && cd fluteband-omr
# скопируйте сюда содержимое dist-space-gradio/
git add -A && git commit -m "FluteBand AI: сервис распознавания" && git push
```

Если вы **обновляете уже выложенное пространство** и набор моделей в пакете сменился (так было при
переходе на закреплённую версию движка), сначала удалите старые модели, иначе в репозитории окажутся оба
набора и 300 МБ вместо 150:

```bash
rm models/*.onnx          # в PowerShell: Remove-Item models\*.onnx -Force
# затем скопируйте содержимое dist-space-gradio/ и запушьте
```

4. Пространство соберётся само (несколько минут: Python, FastAPI, Gradio и движок `homr` с ONNX).
5. Проверьте, что сервис жив: `https://имя-fluteband-omr.hf.space/health` → `{"status":"ok",…}`,
   `…/engines` → доступен `homr`. На вкладке **App** есть страница проверки: загрузите фото и получите
   MusicXML (ею удобно убедиться, что движок работает, ещё до телефона).

### 5.3. Проверить пакет до выкладки (как на бесплатном тарифе)

```bash
docker build -f dist-space-gradio/Dockerfile.test -t fluteband-gradio dist-space-gradio
docker run --rm -p 7860:7860 --cpus=2 --memory=4g fluteband-gradio
curl http://127.0.0.1:7860/health
```

`Dockerfile.test` повторяет сборку пространства (те же `requirements.txt` и `packages.txt`), но Hugging Face
его не читает — он ищет файл с именем ровно `Dockerfile`. Именно так найдены три ошибки четырнадцатого
круга: набор моделей для видеокарты вместо процессорного, гонка двух распознаваний за один архив моделей
и пояснения вместо имён пакетов в `packages.txt`.

Отдельная проверка того, что моделей движку **хватает** и он ничего не скачивает, идёт с выключенной сетью
в окружении самого пространства (Python 3.10, закреплённый `homr==0.6.2`):

```bash
docker build -t fluteband-space-final <контекст с файлами пакета>
docker run --rm --network none --cpus=2 --memory=4g fluteband-space-final
```

Сеть выключена намеренно: если движок захочет скачать модель, запрос упадёт — это и есть доказательство,
что набор моделей в репозитории соответствует версии движка.

### 5.4. Если у вас платный план или другой хостинг

Docker-вариант никуда не делся: `npm run pack:space` собирает `dist-space/` (сервис + `Dockerfile` + шапка
`sdk: docker`) — тот же сервис, но его можно выложить на Hugging Face с платным планом, на Render
(бесплатный веб-сервис из Docker; засыпает после 15 минут простоя, первый запрос после сна — до минуты)
или на Fly.io (небольшой бесплатный лимит). Если не хочется никаких аккаунтов — сервис можно поднять на
своём компьютере и открыть наружу бесплатным туннелем:

```bash
npm run omr:real                       # сервис на http://127.0.0.1:8000
cloudflared tunnel --url http://127.0.0.1:8000   # выдаст публичный https-адрес
```

## 6. Связать приложение с сервисом

1. Откройте приложение на телефоне или компьютере → вкладка **«Сканировать»**.
2. В поле **«Адрес сервиса распознавания»** впишите адрес Space: `имя-fluteband-omr.hf.space`
   (схему можно не писать — подставится `https://`). Адрес хранится на устройстве.
3. Нажмите **«Проверить»** — должно появиться, что сервис отвечает. Затем снимайте ноты камерой.

Чужой сервис трогать не нужно: `dist-space/` — это ваш собственный экземпляр.

## 7. Что проверить после выкладки

- [ ] `https://адрес/index.html` открывается, видны «Библиотека / Сканировать / Минус».
- [ ] Заголовки применились (для Netlify): `curl -I https://адрес/service-worker.js` → в ответе
      `cache-control: no-cache, no-store, must-revalidate`, а у манифеста —
      `content-type: application/manifest+json`.
- [ ] В консоли браузера (DevTools → Application → Service Workers) виден активный service worker
      с областью вашего адреса, а в Cache Storage — кэш `fluteband-shell-…` с 40 файлами.
- [ ] Режим «офлайн» в DevTools: страница перезагружается и работает (это уже проверено на сборке).
- [ ] **Камера** на телефоне открывается по HTTPS (по `http://` браузер камеру не даст).
- [ ] Установка на телефон: «Добавить на главный экран» — приложение открывается без адресной строки.
- [ ] Сервис: `…/health` отвечает, `…/engines` показывает доступный `homr`.
- [ ] Полный круг: фото страницы → минус играет, тональность и темп меняются, экспорт MIDI/WAV работает.

## 8. Что честно сказать про бесплатные тарифы

- **Первый запрос после простоя медленный.** Бесплатные пространства спят: обращение их будит. Модели
  движка лежат в репозитории, поэтому в облаке ничего не скачивается, но сессии ONNX поднимаются внутри
  первого распознавания.
- **Ядер меньше, чем дома.** Пакет проверен в контейнере ровно в условиях бесплатного тарифа (2 ядра,
  4 ГБ) — измерено:

  | Страница | Дома, 16 ядер | На 2 ядрах | Результат |
  |---|---|---|---|
  | демо-страница (разреженная), полный режим | ~6–8 с | **24 с** | 4 такта, минус «march» — как дома |
  | плотная «фортепиано + блокфлейта», полный режим | 32.4 с | **130 с** | 26 тактов, 229 событий, F-dur, 2/4 |
  | та же страница, режим «только мелодия» | 9.6 с | **44 с** | 26 тактов, мелодия та же (86 из 86 нот), 12 станов → 4 |
  | вторая страница сборника (70 тактов), полный режим | — | **209 с** | мелодию выделить не удалось — распознана вся страница |
  | повтор того же запроса | — | **0.1 с** | сработал кэш результатов сервиса |
  | два разных запроса одновременно | — | 23 с и 46 с | второй ждёт первый: распознавания идут очередью (у каждого своё время ~23 с) |

- **Цель 15 секунд** на плотной странице на бесплатном тарифе не достигается: быстрый режим («только
  мелодия») ускоряет примерно вдвое, но и его мало. Это ограничение площадки, а не приложения: сервис
  считает на двух ядрах, которые даёт бесплатный тариф.
- **Мелодию удаётся выделить не всегда.** Геометрический поиск станов сработал на одной из четырёх
  проверенных страниц; в остальных случаях сервис честно распознаёт всю страницу и пишет об этом
  предупреждением, а не выдаёт пустой результат.
- **Предел времени на распознавание** — 240 с (переменная `RECOGNIZE_TIMEOUT`). Если площадка оборвёт
  запрос раньше (у платформ бывают свои пределы на длину запроса), ученик увидит ошибку: тогда снимайте
  страницу по половине или поднимите тариф.
- **Данные.** Пьесы и настройки хранятся на устройстве ученика (IndexedDB), на сервер уходит только
  фото страницы — и только на время распознавания. Storage Bucket пространству не нужен: сервис ничего
  не хранит, фото удаляется сразу после распознавания.
- **Нигде не нужна карта.** Все площадки выше — с бесплатным тарифом; платные функции не используются.

## 9. Что проверено до выкладки (чтобы не сюрпризов)

- Сборка приложения: 46 файлов, 0.45 МБ, ни одного пути от корня сайта, офлайн-оболочка совпадает с файлами.
- Проверка в подкаталоге (как GitHub Pages): 5 проверок статики + 11 офлайн-проверок, все зелёные —
  приложение открывается с выключенной сетью, service worker управляет страницей, минус строится.
- Проверка для Netlify (приложение в корне сайта): 4 проверки + 11 офлайн-проверок, все зелёные.
  Отдельно проверен и худший случай — **с включёнными «красивыми адресами»** (`npm run check:netlify:pretty`):
  главная страница уходит перенаправлением `301` на `/`, и всё равно вся оболочка (40 адресов) ложится
  в кэш и приложение открывается без сети. Именно из-за этого случая кэширование оболочки переписано:
  раньше один такой адрес отменял установку кэша целиком (`cache.addAll`), и офлайна не было бы вовсе.
- **Gradio-пространство**: пакет собран (21 файл, 150 МБ, из них 150 МБ — модели движка), проверен
  автоматическими тестами (шапка `sdk: gradio`, `app_file`, порт, правило git-lfs, состав моделей) и
  запущен в контейнере ровно как на бесплатном тарифе: `/health` ответил за 3 с, `/engines` показал
  доступный `homr`, корень отдаёт страницу Gradio, а наши маршруты при этом работают. Распознавание
  проверено в обоих режимах, в облаке не скачано **ни одного** файла моделей.
- **Три ошибки, видимые только при настоящем запуске Gradio-пространства, найдены и исправлены:** в пакет
  попал набор моделей для видеокарты вместо процессорного (в облаке движок полез их скачивать); два
  распознавания (прогрев плюс запрос ученика) делили один архив моделей, из-за чего одно падало с
  `FileNotFoundError`; в `packages.txt` были пояснения на русском, а Hugging Face читает этот файл через
  `xargs` — слова стали именами пакетов и сборка упала на `Unable to locate package #`. Исправлено
  составом пакета, очередью распознаваний и чистым списком библиотек; локальная проверка теперь ставит
  библиотеки из того же файла той же командой, поэтому такая ошибка больше не дойдёт до облака.
- **Набор моделей приведён в соответствие версии движка** (четвёртая ошибка того же круга, нашлась уже
  после выкладки, при сборке настоящего пространства): на Python 3.10 pip ставит `homr 0.6.2`, которому
  нужны модели **331**, а в пакете лежали модели **396** от 0.7.0 — движок начал скачивать свои во время
  запроса. Версия движка закреплена, набор заменён (150.3 МБ), при старте пространство сверяет набор с
  ожиданиями движка и пишет расхождение в журнал, а флаг `--gpu` передаётся только знающей его версии.
  Проверено запуском сервиса **без сети**: распознавание проходит, скачиваний нет.
- **Прогрев движка** переделан по замеру: полное пробное распознавание при старте занимало очередь и
  задерживало первый запрос ученика на 25 с, ничего не ускоряя (53 с против 28 с). Теперь при старте
  модели только читаются с диска.
- Образ сервиса (Docker-вариант): собран (1.87 ГБ), контейнер поднимается healthy, работает не от root,
  `/engines` показывает доступный `homr`, распознавание отдаёт тот же нотный текст, что и домашний прогон
  (одна нота из 229 отличается — в контейнере движок использует модели под процессор, а дома стоят fp16).
- Четыре ошибки, видимые только при настоящем запуске контейнера, найдены и исправлены: проверка установки
  движка, системные библиотеки для OpenCV, права на каталог моделей и понятный ответ вместо
  «Internal Server Error» при нехватке времени.
